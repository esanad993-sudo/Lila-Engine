# LILA ENGINE — Source Bundle (Engine + DSL)

The complete engine: the **LILA DSL** and its two implementations.
**No games included** — this is the tool and the machine, not content.

```
LILA source (.lila)          The DSL — one file, declarations + fns
      │
      ▼
compiler/  (Rust)            DSL front/back-end -> .libyte bytecode
      │
      ▼
runtime/   (Zig)             VM + 2D/3D renderer + audio, native + wasm
```

## What each half is

### `docs/` — the DSL definition
| File | Contents |
|---|---|
| `LANGUAGE.md` | The full language reference (v7 base + v11/v12 3D): source layout, types, `#atoms`, entities, statements, expressions, arrays, mat4/quat, indexed meshes, Z-buffer profile knob, determinism rules |
| `SPEC.md` | Bytecode/engine spec |

### `scripts/` — build system
| File | Role |
|---|---|
| `build_engine.sh` | Profile knob -> regenerates `engine_config.zig` -> builds runner + wasm. Profiles: default/big/huge; knobs: `mem_mb max_ent max_verts max_instr ... zbuffer3d=0/1` |
| `mkhtml.py` | Bundles `lila.wasm` + a `.libyte` into one self-contained HTML page |

## Build

Compiler (Rust):
```sh
cd compiler && cargo build --release
# -> target/release/lilac
# ./lilac build game.lila -o out.libyte ; ./lilac disasm out.libyte
```

Runtime (Zig 0.16):
```sh
ZIG=/path/to/zig scripts/build_engine.sh            # default profile
ZIG=/path/to/zig scripts/build_engine.sh zbuffer3d=1 # Z-buffer profile
# -> runtime/runner (native) + runtime/lila.wasm
zig test runtime/src/test_v12.zig                    # engine test suites
```

Requires: Rust (edition 2021), Zig 0.16.x. No other dependencies — the whole
engine builds with the two toolchains alone.

## Invariants the codebase maintains

- **Integers only**: all spatial math Q24.8 fixed-point; trig = 4096-entry LUT;
  no floats in game state -> bit-exact determinism across platforms.
- **Determinism contract**: same input script -> identical frame stream and
  audio samples on native and wasm; optimizer on/off changes speed, never bits.
- **One flat buffer**: engine state is a comptime-laid-out flat map — hosts poke
  raw offsets; snapshot/rewind is a memcpy.
- **Contracts**: legacy .libyte files load byte-identically across all engine
  versions (version-gated opcodes).


## v14 quality pass (robustness + visual fidelity)

The engine keeps its performance profile and determinism guarantees; what
changed is how it fails and how it looks:

**Never a panic.** The loader treats every .libyte as hostile: truncation
detection on every section (ERR_TRUNCATED, finally), validated typed-field
geometry, music/anim/sfx count limits, fn-table range checks, huffman
length neutralization, and a transactional load that zeroes the engine
counts on failure. The VM wraps jump arithmetic, guards stack underflows,
and soft-lands every masked operand. hotSwap rolls back the full engine
schema when a swap fails — watch mode never runs on corrupted state.
`scripts/build_engine.sh --test` runs the whole suite, including a
2000-round mutation fuzz against real compiler output.

**Diagnostics like a real toolchain.** `lilac` errors carry line:col and
render with the source excerpt and a caret:

```
$ lilac build bad.lila
error: line 2:8: unexpected token in expression: Semi
   1 | fn init() {
   2 |   px = ;
   2 |        ^
```

CLI flags missing values are usage errors, not panics. The checker
rejects format-overflow inputs (screen dims, anim segments, music voices,
table entries, fn counts) at compile time instead of corrupting the file.

**The rasterizer finally draws what the data says.** Gradient sprites
interpolate per-vertex RGBA (92 distinct colors where there used to be
2). Half-pixel sample centers kill the double-blended seams between
triangle pairs. Additive blending saturates instead of wrapping to
black. And it got 2.4x FASTER in the process — the per-pixel edge
functions are incremental (adds, not multiplies) and the clear is
precomputed row templates.

**Same bytes out.** The engine-state hash chain (input log + per-frame
Wyhash) is bit-identical across every one of these changes — verified
against a recorded 300-frame baseline. The .libyte output of the refactored
compiler is byte-identical too.

## v15 visual fidelity pass (depth cue + gamma-correct blending)

Two renderer-quality items, same rules as v14: keep the deterministic
engine untouched, keep performance, make the pixels tell the truth.

**The 3D depth shading curve was recalibrated to the engine's actual
scene scale.** The v1 curve faded linearly to a 31% floor by 6.5 world
units — but LILA scenes are authored at hundreds of units (the depth
token's horizon is 512), so every object in a real game rendered on the
floor: the demo's hero cube filled a third of the screen at 31%
brightness, with zero depth separation anywhere. The replacement is the
physical inverse-square law onto a 37.5% fog floor:

```
shade(d) = 96/256 + (160/256) * K / (K + e^2),  e = max(d - 1u, 0)
K = (400 units)^2          depth:   1    50   150  293(hero)  512
                           v15:  100%   99%   92%    78%      61%
                           v1:   100%   31%   31%    31%      31%
```

Smooth (no clamp knee), monotone, one i64 division per triangle (never
per pixel — rasterizer cost unchanged). The demo cube's luminance went
49 -> 128, and its near/far faces now differ (83% vs 74%): internal
depth gradient, visible for the first time. This is a deliberate,
documented change to rendered output: the 300-frame hash chain is
re-baselined (the vertex stream carries the shaded colors and lives in
engine memory); the .libyte format and compiler output are untouched
(still byte-identical, SHA256 72b8a82a).

**Gamma-correct blending, as an opt-in knob.** 8-bit sRGB values are
perceptual codes, not light: blending them directly puts every
intermediate in the mud (a 50/50 black/white mix lands on code 128 =
22% light, not 50%). `--gamma` on the runner (or `gamma_blend=1` /
`GAMMA_BLEND` in the build profile) switches the CPU rasterizer's
blends, additive accumulation, gradient interpolation and noise
darkening to LINEAR light through two comptime-baked sRGB LUTs
(256-entry decode, full 64K-entry encode; the hot path never touches a
float). Alpha stays coverage — it is never converted. The 50/50 blend
now lands on 188. The LUT pair round-trips exactly, so opaque and flat
pixels are bit-identical in both modes and take no conversion cost:
gamma-on measured 0.095 ms/frame vs 0.093 off (2%, this demo's blend
mix). Pixel-output-only: a `--gamma` run produces a byte-identical
hash-chain movie, and `test_raster.zig` pins that proof (plus the
128-vs-188 anchors, blend goldens in both spaces, and the c.mem
isolation check). The WebGL uber-shader should implement the identical
decode/blend/encode when the knob is on.

**Verification.** A/B build with the old curve reproduces the v14
300-frame movie bit-for-bit (proving the knob and all other v15 changes
are state-neutral); the new chain self-replays 300/300; Rust 58 tests +
Zig 61 test invocations (11 new) all pass with zero warnings in both
toolchains; wasm builds unchanged.
